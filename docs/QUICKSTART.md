# Start with the decision on your desk

Choose one skill from the [catalog](../catalog/README.md). Read its Purpose and Input sections, then provide the project evidence you already have. You do not need to complete a form before asking for help.

## Three starting requests

**A doubtful date**

"Use $estimation-advisor. We have a fixed target, incomplete interface requirements, and these three estimates. Explain what is supportable before we commit."

**A sponsor update**

"Use $status-report. Draft a one-screen update as of 16 October. Here are the approved baseline, current forecast, accepted work, open issues, and decisions needed. Use the evidence even if the status is uncomfortable."

**A release decision**

"Use $release-readiness. Compare this release's evidence with our acceptance criteria. Distinguish missing evidence, failed gates, and actual authorized exceptions."

Use the explicit skill invocation supported by your assistant, or ask it to read the selected `SKILL.md` and follow it. Named adjacent skills are optional handoffs; the entrypoints explain the required artifacts when those skills are unavailable.

## Bring partial context honestly

A forecast is not a baseline, a proposed owner is not an accepted assignment, and a test plan is not a test result. Include the source date and approval record where available. Ask for a draft with unknowns if you are not ready for a decision.

## Learn while doing

Read the worked examples after your first draft. Compare the flawed and corrected versions with your own artifact. Use the Common Pitfalls section as a review aid, then inspect the underlying evidence. A completed template is only the beginning of that review.

Try the [software walkthrough](walkthroughs/software.md) or [migration walkthrough](walkthroughs/migration.md) to see how artifacts connect across a project.
